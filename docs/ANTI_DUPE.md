# Anti-dupe behavior

## Core rule

The default mode multiplies resources that were not directly placed by a player. It does not multiply a player-created loop of items becoming blocks and then becoming more items.

Example with a `2x` global multiplier:

```text
Natural stone -> mine -> 2 cobblestone
Place one cobblestone -> mine -> 1 cobblestone
Place it again -> mine -> 1 cobblestone
```

## Placement recording

`BlockItem.place` opens a bounded, nestable placement transaction. Successful server-side block writes that create or replace a non-air state become candidates. Every candidate is marked only when the outer placement returns success; failed placements discard their candidates. This captures ordinary blocks plus multi-block placements such as doors and beds without scanning nearby positions.

The record is persistent. Restarting the server does not reset protection.

Items that place blocks without using `BlockItem.place` need explicit compatibility support. Commands, structures, and world-editing APIs are intentionally treated as world generation unless another integration marks their output.

## Break cleanup

- Successful player break: remove the marker after the break event.
- Canceled player break: keep the marker.
- Explosion: remove the marker only when the original block was actually replaced.
- Automated drop path: retain the marker during loot calculation and clear it only after a successful non-piston block replacement.
- `0x` rule: suppress loot and still clear a successfully broken block's marker.

Loot multiplication also checks the exact original level, position, and state before it can claim a session. A nested loot call for another block receives its own context and cannot consume the outer block's provenance decision. Fabric fake players use the automation source gate rather than inheriting normal player permissions.

## Pistons

A piston moving-block entity derives the source position from its destination and movement direction. It consumes the source marker and writes protection at the completed destination.

`conservativePistonProtection` defaults to `true`. With that setting, even a natural block moved by a piston becomes protected at its destination. This intentionally favors a safe false positive over an exploitable false negative when another mod changes piston movement or provenance cannot be recovered cleanly.

Piston provenance flags are stored with the moving block entity so an in-progress move remains safe across a save and restart.

## Falling blocks

When sand, gravel, concrete powder, an anvil, or another falling block becomes an entity, the origin marker is consumed and attached to that entity. If the entity successfully places a block at its landing position, the destination is marked. The entity flag is persisted while the entity is saved.

If the falling block turns into an item instead of placing a block, no destination is marked.

Concrete powder becoming matching concrete is an explicit same-resource transformation, so a placed powder block cannot become natural merely by hydrating.

## Same-position transformations

Protection is preserved for:

- Property-only changes to the same block, except known generated growth
- Soil-family changes such as dirt to farmland or dirt path
- Matching logs, wood, stems, and hyphae before and after stripping
- Copper weathering, de-weathering, waxing, and wax removal
- Matching concrete powder to concrete
- Living/dead coral counterparts
- Cauldron variants

An unrelated replacement, such as placed stone becoming diamond ore through a command or another mod, does not inherit the stone marker. Crop, nether wart, cocoa, berry bush, cave-vine, and kelp growth is treated as newly generated rather than permanently carrying the seed or immature block's marker.

## Growth and generated resources

The mod tracks direct block placement, not all causal descendants. These examples remain natural by default:

- Logs generated when a placed sapling grows
- Mature crops grown from planted seeds
- Budding amethyst growth
- Cobblestone and basalt generator output
- Snow or ice formed by world conditions
- Blocks generated by terrain or structures

Servers that do not want a renewable resource multiplied can blacklist the block or its tag, set it to `1x`, or use whitelist mode.

## Remove-before-drop integrations

Some machine integrations clear a block before asking Minecraft for its loot. When a marked position is replaced, a per-level compatibility cache keeps it protected for two ticks. The cache expires old entries incrementally and holds at most 4,096 positions per level.

If that limit is exceeded, the cache fails closed for the remaining two-tick window: an unknown queried position is considered protected rather than potentially multiplied. A game-time rollback clears stale entries. Machines that calculate loot outside this short vanilla-compatible window require their own integration.

## Block entities

Block entities are forced to vanilla behavior by default. This protects chests, barrels, furnaces, hoppers, shulker boxes, decorated pots, and modded containers from accidental NBT or inventory multiplication.

A server may allow a specific block through `blockEntityAllowlist`, but the administrator accepts responsibility for that block's drop behavior.

## Protection modes

| Mode | Natural block | Player-placed, protection ON | Player-placed, protection OFF |
| --- | ---: | ---: | ---: |
| `NATURAL_ONLY` | configured multiplier | `1x` | configured multiplier |
| `ALL` | configured multiplier | configured multiplier | configured multiplier |
| `PLAYER_PLACED_ONLY` | `1x` | configured multiplier | configured multiplier |

Turning `smartPlacementProtection` off relaxes the placed-block exclusion in `NATURAL_ONLY`; it does not relax the natural-block exclusion inherent to `PLAYER_PLACED_ONLY`. Provenance is still recorded and evaluated while protection is off, so the source mode or protection setting can be changed later without resetting world history.
